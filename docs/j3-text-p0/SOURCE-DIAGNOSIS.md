## Compare theme timeout: order and the Applied badge

In18e04460 `handleGenerate()` sets the blank's progress overlay, then awaits `ensureThemeReady()` at569. `!readiness.ready` sets the error/toast and returns at589. Text Labs session acquisition starts only at1105; payload construction is at1131 and ordinary Text Labs dispatch at1249. Therefore **a theme-readiness rejection sends no Text Labs request** through this invocation. Directly replaying a guessed Compare request against TL would test a different boundary and could not explain this preflight failure.

`ensureThemeReady()` checks presentation + semantic theme fingerprint and a non-null applied request identity. If a Director mutation is in flight, or a connected Director must update idle/stale selection, it waits for the authoritative acknowledgement. `waitForAuthoritativeTheme()` uses20,000ms. The same function body and default budget exist in the pre-flip Studio snapshot; source origin includes `83a6640b` dated18 July2026. Wrong-presentation or different-theme acknowledgements cannot safely release generation. A matching semantic applied theme can remain authoritative under a replacement transport request after reconnect. Persisted Layout / neutral fallback exists for specified disconnected/failed states and must remain distinct from a pending locally chosen theme.

The theme handshake is Director WebSocket `set_theme` with `data.request_id`, `theme` and `presentation_id` (`hooks/use-deckster-websocket-v2.ts`:3446-3465), followed by Director `theme_sync`; it is not an iframe acknowledgement. `requestThemeSyncForPresentation()` (`app/builder/page.tsx`:3100-3194) starts the global20-second timer when it sends the first request and deduplicates an existing matching syncing/applied request. A later Generate can share that already-running timer. The element's wait has its own20-second ceiling, but can return `failed` earlier when the original request timer expires. The offline replay models an existing request with3seconds remaining and proves failure at3seconds, with no duplicate send. It cannot establish when the actual request began relative to frame reload or the Compare click; no exact WS capture survives in this run.

The virtual-clock replay proves missing ack ->timeout20,000ms and matching ack ->ready; it does not assert what the real Director sent. Root reports Compare's later screenshot shows `Applied` in Director while the panel still says theme timed out. `components/builder/chat-input.tsx` renders Applied from the latest `themeSyncStatus==='applied'`; `app/builder/page.tsx`:2246-2255 accepts the latest request's terminal update. Actual `applyThemeSyncResponse()` explicitly accepts late same-request `applied` after `failed`; the replay proves this, rejection of unrelated request IDs, and protection against a late `syncing` downgrade. The earlier generation-panel error is not automatically cleared by the theme event. A late successful ack can therefore leave an earlier timeout message visible. **This is a plausible source-supported sequence, not proof of its exact occurrence**; an identity mismatch or stale state remains possible without WS/request records. Do not bypass theme authority to make the badge and panel appear consistent.
